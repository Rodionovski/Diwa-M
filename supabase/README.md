# Підключення адмінки Diwa-M

Сайт залишається статичним сайтом на Render. Supabase надає PostgreSQL, Storage та Auth.
Адмінка: `/admin`. Без конфігурації сайт показує початковий прайс і фото, а кабінет повідомляє про необхідність підключення.

## 1. Створіть Supabase-проєкт

1. У https://supabase.com/dashboard створіть новий проєкт та збережіть пароль бази в менеджері паролів.
2. У SQL Editor виконайте весь `schema.sql`, потім весь `seed.sql` з цієї папки. Схему виконують один раз; seed можна повторювати — він не перезаписує зміни.
3. У налаштуваннях API скопіюйте Project URL та **публічний publishable / anon key**. `service_role` / secret key для сайту використовувати не можна.

## 2. Створіть адміністратора

1. У Authentication → Providers → Email вимкніть публічну реєстрацію (Allow new users to sign up).
2. У Authentication → Users → Add user → Create new user створіть користувача з поштою та сильним паролем. Увімкніть Auto Confirm User. Передайте пароль працівнику окремим захищеним каналом.
3. Виконайте SQL, замінивши пошту на адресу створеного користувача:

```sql
insert into public.admin_users (user_id)
select id from auth.users where lower(email) = lower('admin@example.com')
on conflict (user_id) do nothing;
```

4. Перевірте, що рядок додано. Без нього користувач не зможе редагувати сайт, навіть якщо увійде.
5. Для кожного працівника краще створити окремий обліковий запис і додати його так само.

Відкликати доступ:

```sql
delete from public.admin_users
where user_id in (select id from auth.users where lower(email) = lower('admin@example.com'));
```

Відновлення пароля: власник проєкту скидає пароль користувачу через Supabase Dashboard. У публічній адмінці немає реєстрації чи самостійної видачі прав.

## 3. Render

Публічні параметри поточного проєкту вже записано в `.env.production` і буде включено в продакшн-збірку. Локальні значення — у проігнорованому `.env.local`.

Для іншого Supabase-проєкту оновіть `.env.production` або в **наявному** сервісі `diwa-m` відкрийте Environment і задайте параметри нижче (значення з Render мають пріоритет):

```text
NODE_VERSION=22
VUE_APP_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VUE_APP_SUPABASE_ANON_KEY=YOUR_PUBLIC_ANON_OR_PUBLISHABLE_KEY
```

Ці параметри підставляються під час **збірки**, тому після їх додавання потрібен новий deploy.

Для Static Site:

- Build Command: `npm ci && npm run build`
- Publish Directory: `dist`
- Збірка автоматично створює HTML-сторінки для `/admin`, `/services` і `/gallery`, тому прямі посилання працюють без ручних rewrite-правил. Для додаткових майбутніх маршрутів можна налаштувати Redirects/Rewrites: Source `/*`, Destination `/index.html`, Action **Rewrite** (не Redirect).

Збережіть чинний тип сервісу та адресу. Не створюйте новий сервіс замість наявного.
У Supabase Authentication → URL Configuration вкажіть Site URL `https://diwa-m.onrender.com`.

Для локального запуску скопіюйте `.env.example` у `.env.local`, заповніть значення та виконайте `npm run serve`.

## 4. Перевірка після підключення

1. Відкрийте `/admin` без входу — доступна тільки форма входу.
2. Увійдіть користувачем без запису в `admin_users` — редагування недоступне.
3. Увійдіть адміністратором. Змініть одну ціну, додайте тестове фото з описом і натисніть «Опублікувати зміни».
4. В іншому браузері без входу перевірте `/services`, `/gallery` і три перші фото на головній. Оновіть сторінку для отримання останніх змін.
5. Відкрийте дві вкладки адмінки. Збережіть різні зміни по черзі: друга має повідомити про конфлікт, а не перезаписати першу.
6. Перевірте вихід, пряме відкриття `/admin` та `/gallery`, і завантаження файлу понад 5 МБ — його має бути відхилено.

## Як користуватися

- Фото: завантаження JPG/PNG/WebP до 5 МБ, опис, порядок стрілками, прибирання з галереї.
- Прайс: розділи, групи, послуги, текстові ціни та примітки.
- Нові фото спочатку зберігаються лише у чернетці браузера. До публікації закриття сторінки скасовує правки.
- Після «Опублікувати зміни» правки потрапляють у спільну базу; GitHub-коміт і новий deploy для зміни контенту не потрібні.
- RLS дозволяє читати публічний контент усім, але змінювати його та завантажувати файли — лише призначеним адміністраторам.
- Фото після незавершеної публікації можуть залишитися у Storage. Повторна спроба в тій самій вкладці використовує вже завантажені файли. Файли не видаляються автоматично після мережевої помилки, бо база вже могла прийняти зміни.
- Прибрані опубліковані фото залишаються у Storage, щоб старі відкриті вкладки не отримували зламані зображення. Вони більше не показуються в галереї. Не видаляйте файли, на які ще посилається `site_content`.
- У разі недоступності бази публічний сайт показує останній контент поточної вкладки або початковий контент зі збірки; прайс і галерея показують повідомлення, що останні зміни недоступні.
- Резервні копії: зберігайте експорт `site_content`, список адміністраторів та копії Storage-файлів. Умови резервування залежать від вибраного плану Supabase.
